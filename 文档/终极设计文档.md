## 1. 核心问题与设计哲学

### 1.1 要解决的真问题

```
不是："怎么把更多内容总结得更好"
而是："怎么在噪音中最快发现从冷到热的信号"
```

这是两个完全不同的方向。前者是"百科"，后者是"雷达"。百科有覆盖率压力，雷达只关心**变化**。

### 1.2 四条设计哲学

**① 热点 = 增长率，不是绝对值**

`BTC` 永远高频，但它不是 alpha。真正的信号是：某个词 7 天均值每小时 20 次提及，突然变成 900 次。这个 **45 倍**才是信号，不是 `BTC` 稳定的 5000 次。

**② LLM 只在最后一公里介入**

统计的活让代码干（更快、更准、零成本），检索的活让向量干，LLM 只做一件事：对**已经被数学确认为热点**的内容，用人话解释"为什么热、热在哪、怎么看"。

**③ 做雷达，不做百科**

雷达的价值是**发现新出现的信号**，不是描述已知全貌。核心竞争力是**早**，不是**全**。

**④ 复杂度是第一风险（方案 4 的核心警告）**

个人开发者最大的敌人不是技术难度，是系统复杂度。一上来想做全套微服务 + ClickHouse + Milvus + KOL 图谱 + 多模态——等你把架构图画完，Alpha 已经走了。

> **推论**：Phase 1 必须能**不依赖任何 LLM**就跑起来。只要"热度排行榜"能出来，系统就已经有价值。后面一切都是锦上添花。

### 1.3 信号层级（从高到低）

| 优先级 | 信号类型 | 实现层 |
|-------|---------|-------|
| P0 | 单实体增长率激增 | L2 |
| P0 | 跨源共振（多个平台同时热） | L2 |
| P1 | 共现新组合（新叙事形成） | L3 |
| P1 | 新词出现（基线期从未见过） | L2 |
| P2 | 情绪急转（中性→极度看多） | L1/L2 |
| P2 | KOL 首发 | L1/L2 |

### 3.2 LLM 的精确介入点

整个 pipeline 中，**LLM 只在两处介入**：

- **L5 主力（Phase 2）**：对 Top-K 话题簇做结构化简报，每小时几十次调用
- **L5 日报（Phase 3）**：每日一次用 `qwen3:32b` 做跨热点总评

**L1 的"小模型兜底抽实体"默认关闭**（设计文档 2 留了这个口子，但实测下来词典 + 正则的覆盖率在加密领域足够高，开启会导致 LLM 调用量显著上升，ROI 不合算）。只在 Phase 3 监控到"词典覆盖率<70%"时才考虑开启。

日 LLM 调用量级控制在**几十到几百次**，不是几万次。

```

  与近 24h 消息对比，汉明距离 > 3 → 非重复，通过

  词典命中:  [Base, Virtuals, AI_Agent]

  ↓ 写入 entity_mentions（4 条记录）

  ↓ L2 热度统计（每 15 分钟）

  ↓ L3 共现网络

  (AI_Agent, Virtuals, Base) 三角共现增长 22x → 新叙事确认

  ↓ L4 Embedding 聚类
```

## 5. L0 归一化与去重

**目标**：把数据量砍掉 30~50%，消除复读机效应。

### 5.1 归一化（normalizer）

`services/l0_normalizer.py` 把三个原始表统一成 `NormalizedMessage`：

```python
@dataclass
class NormalizedMessage:
    raw_id:        int                # 关联原始表 id
    raw_source:    str                # "twitter" | "binance_square" | "discord"
    text:          str                # 清洗后正文（保留 $TICKER、情绪 emoji）
    author:        str                # 统一格式（Discord 用 "#channel @user"）
    author_weight: float              # 默认 1.0，KOL 查表后覆盖
    ts:            datetime           # 统一 UTC
    engagement:    int                # 三个源口径不同，归一化后存
    simhash:       int                # 64 位指纹
```

**清洗规则**：

- 移除纯链接帖、纯表情帖、少于 5 个有效词的帖子
- 保留情绪 emoji 作为信号（🚀 / 💀 / 🤔）
- 统一 `$TICKER` 大写
- 广告账号过滤（低粉 + 高频 + 固定模板） ← Phase 2 再做

### 5.2 去重（两阶段，Phase 1 只做阶段一）

**阶段一：SimHash（毫秒级，Phase 1 起跳）**

```python
# services/l0_dedup.py

```

**阶段二：Embedding 精筛（Phase 3 升级）**

数据量稳定后再上 `bge-m3`，cosine ≥ 0.92 判重。SimHash 抓不到的"中英互译/语义转述"交给它。

**Phase 1 只做 SimHash 就够**，能砍掉 30~50% 的 LLM 调用量，这是 ROI 最高的一步。

### 6.1 三层抽取（只做前两层）

**第一层：正则（已在 prefilter 里）**

```python
$TICKER:     \$([A-Za-z一-鿿][A-Za-z0-9一-鿿]*|\d[\d.]*[BMK]?)

```

**第二层：词典（YAML 外置，持续维护）**

`dictionaries/` 目录（新增）：

```yaml
# tickers.yaml
BTC:   { aliases: [比特币, bitcoin, 大饼, 老大], type: layer1 }
```

**重要**：现有 `prefilter.py` 的 `COIN_KEYWORDS_EN / COIN_KEYWORDS_ZH` 已经是词典的雏形，迁移到 YAML 后，prefilter 和 entity_extractor 共用同一份数据。

**第三层：小模型兜底（默认关闭）**

只在 Phase 3 发现"词典覆盖率<70%"时再考虑开启。开启后用 `qwen3:8b` 批处理 50 条/次做结构化抽取。

### 6.2 改造 prefilter

**关键设计**：不新建模块，而是**扩展 `prefilter.classify`** 的返回值：

```python
# 原来（现在）
@dataclass(frozen=True)
class FilterDecision:
    keep: bool
    reason: str

# 改造后
@dataclass(frozen=True)
class FilterDecision:
    keep:     bool
    reason:   str
    entities: list[Entity]    # 新增：顺带产出实体标签
```

这样 `prefilter_split` 既做过滤又做实体抽取，扫一次文本完成两件事，比拆成两个模块效率更高。

### 6.3 情绪打分（轻量）

同步在 L1 算一个简单的情绪分：

```python
BULLISH_STRONG = {"ape", "exploding", "moon", "100x", "🚀🚀🚀", "send it"}

```

## 7. L2 热度统计（系统核心）

**这是整个系统最值钱的一层。** 它决定了你能看到什么、多快看到。

### 7.1 核心算法：增长率

```python
def compute_growth_rate(
    entity: str,
    window_end: datetime,
    short_hours: int = 1,
    baseline_days: int = 7,
) -> float:
    # 短窗：最近 N 小时提及次数
    short_count = count_mentions(entity, window_end - timedelta(hours=short_hours), window_end)

    # 基线：过去 7 天（排除最近 short_hours）的每小时平均
    baseline_start = window_end - timedelta(days=baseline_days)
    baseline_end   = window_end - timedelta(hours=short_hours)
    baseline_total = count_mentions(entity, baseline_start, baseline_end)
    baseline_per_hour = baseline_total / (baseline_days * 24 - short_hours)

    # 平滑因子防止冷启动除零："一个词突然出现 2 次"不应触发警报
    SMOOTHING = 2.0
    return short_count / max(baseline_per_hour, SMOOTHING)
```

### 7.2 多时间窗口（Phase 2 再加）

| 窗口 | 基线 | 用途 |
|------|------|------|
| 1h | 7 天均值 | 主力窗口，捕获突发热点 |
| 6h | 30 天均值 | 捕获中期上升趋势 |
| 15min | 24h 均值 | 超短期脉冲，配合实时告警 |

### 7.3 综合热度评分

```python
def final_score(rec: HotnessRecord) -> float:
    growth   = rec.growth_rate                    # 主信号
    cross    = 1 + 0.3 * (rec.cross_source - 1)  # 跨源加权
    eng      = math.log1p(rec.engagement_sum)    # 互动对数加权
    kol      = 1 + 0.5 * rec.kol_flag            # KOL 首发 +50%
    novelty  = 2.0 if rec.is_new_entity else 1.0 # 新词 ×2
    return growth * cross * eng * kol * novelty
```

**Phase 1 先只实现 `growth * cross` 两项**，后面三项（eng / kol / novelty）Phase 2 再加。

### 7.4 新词检测

```python
def detect_new_entities(window_end):
    """
    基线期（7 天前）从未出现过、最近 1 小时突然出现 ≥5 次的词
    增长率理论无穷大，单独处理
    """
    recent     = get_entities_in_window(window_end - 1h, window_end)
    historical = get_entities_in_window(window_end - 7d, window_end - 1h)
    return [e for e in recent if e not in historical and recent[e] >= 5]
```

### 7.5 滑动窗口计数器（内存实现）

```python
# services/l2_sliding_counter.py
from collections import defaultdict, deque

class SlidingWindowCounter:
    """
    纯内存，重启重建。
    对高频统计比每次查 DB 快 100 倍。
    """
    WINDOWS = {
        '15min': 900, '1h': 3600, '6h': 21600,
        '24h': 86400, '7d': 604800,
    }

    def __init__(self):
        self._store = {name: defaultdict(deque) for name in self.WINDOWS}

    def add(self, entity: str, ts: float):
        for name in self.WINDOWS:
            self._store[name][entity].append(ts)

    def count(self, entity: str, window: str = '1h') -> int:
        cutoff = time.time() - self.WINDOWS[window]
        deq = self._store[window][entity]
        while deq and deq[0] < cutoff:
            deq.popleft()
        return len(deq)
```

## 8. L3 共现网络（叙事发现核心）

**方案 3 独有的洞察，也是最有远见的设计**。

### 8.1 共现统计

### 8.2 新叙事检测

```python
def detect_emerging_narratives(window_end):
    """
    取 Top-30 热点实体，两两组合，找共现增长率 > 5x 的对
    这些对就是"正在形成的新叙事"
    """
    hot = get_top_k_entities(window_end, k=30)
    emerging = []
    for a, b in combinations(hot, 2):
        cur = cooccur_count(a, b, 1h_ago, now)
        base = cooccur_count(a, b, 7d_ago, 1h_ago) / (7 * 24)
        if cur >= 5 and cur / max(base, 0.5) > 5.0:
            emerging.append({'pair': (a, b), 'growth': cur / max(base, 0.5), 'count': cur})
    return sorted(emerging, key=lambda x: x['growth'], reverse=True)
```

三个词同时频繁出现 = 叙事更成熟。比如 `AI_Agent + Virtuals + Base` 三角共现增长 22x → 不再是偶然，是明确的叙事。

## 14. 调度时序与 worker 改造

### 14.1 现有 worker（需要保留的设计）

`scheduler/jobs.py` 的核心设计：**level1 + level2 串行共用同一 worker 线程**，避免 Ollama 频繁 swap 模型。这个约束在终极方案里**必须继承**——因为 L5 会用到更多模型（14b 常规、8b 紧急、32b 日报），更不能并发。

### 14.2 新的任务时序

```
L0+L1 [持续]: 消费新原始消息 → 归一化 → 去重 → 抽实体 → 写表
              (现有 level1_service 改造点: 拆出 L0+L1，不再做 LLM 摘要)

L2 [每 15 分钟]: 滑动窗口批量计算 → 写 hotness_snapshots
                 (新 job)

L3 [每 15 分钟]: 共现矩阵更新 + 新叙事检测 → 写 entity_cooccurrence
                 (Phase 2 新 job)

L4+L5 [每 1 小时]: 取 Top-K 热点 → bge-m3 聚类 → LLM 简报
                   (Phase 2 新 job，与原 level1/level2 串行)

L5 日报 [每天 1 次]: qwen3:32b 跨热点总评
                     (Phase 3 新 job)

实时触发 (任意时刻):
  growth > 20x → 立即 L5 紧急简报 → L6 推送
  新词 ≥ 5 次 → 标记，纳入下次 L2
```

## 16. 现阶段坚决不做的事

方案 4 的核心警告：**个人开发者最大的敌人是复杂度**。下面这些东西**看起来很想做，但现阶段坚决不做**：

| 不做的事 | 为什么 | 什么时候再考虑 |
|---------|--------|---------------|
| Milvus / Weaviate 向量数据库 | 太重，FAISS 本地文件足够 | 数据量 >1000 万且跨机部署时 |
| Redis | 现阶段内存滑动窗口够用 | 多进程/多机需要共享状态时 |
| 微服务拆分 | 单体 Python 最简单 | 日处理量 >5000 万时 |
| ClickHouse | PostgreSQL 足够 | 热度查询延迟 >1s 时 |
| LLM 做实体抽取（L1 兜底） | 词典+正则覆盖率够 | 词典命中率<70% 时 |
| Kafka/RabbitMQ | 内存队列足够 | 上多实例时 |
| 多模态（图片/视频） | ROI 太低 | 核心流程稳定后 |
| 深度学习自研情绪模型 | 词典版本够用 | 情绪准确率成为瓶颈时 |
| Web 前端 | Streamlit 几十行 > 前端工程几周 | 永远不做，除非商业化 |
| 回测系统 | 这是另一个产品 | 彻底不做 |

## 17. 技术栈与硬件配置

### 17.1 技术栈

| 类别 | 选型 | 理由 |
|------|------|------|
| 数据库 | PostgreSQL（现有） | 成熟，后期可加 pgvector |
| 向量库 | FAISS（本地文件） | 轻量，不上 Milvus |
| Embedding | `bge-m3` (sentence-transformers) | 中英混合最佳，2GB |
| 近似去重 | `datasketch`（SimHash） | 毫秒级 |
| 中文分词 | `jieba` | 轻量，可自定义词典 |
| 聚类 | HDBSCAN | 无需预设簇数 |
| LLM 框架 | Ollama（现有） | 复用 |
| 调度 | 现有 `Jobs` worker | 复用 |
| 消息队列 | 内存队列 | 初期不引入新依赖 |
| 可视化 | Streamlit | 几十行代码 |
| 告警 | Telegram Bot | 简单可靠 |
| ORM | SQLAlchemy（现有） | 复用 |

### 17.2 硬件规划（96G 内存，纯 CPU）

| 组件 | 内存 | 常驻性 |
|------|------|--------|
| `bge-m3` Embedding | ~2GB | 持续常驻（L0/L4 共用） |
| `qwen3:8b` (Q4) | ~5GB | 常驻（紧急简报） |
| `qwen3:14b` (Q4) | ~9GB | 按需加载（L5 主力） |
| `qwen3:32b` (Q4) | ~20GB | 每日 1 次，用后释放 |
| 滑动窗口内存 | 1~3GB | 持续 |
| PostgreSQL 缓存 | 2~4GB | 持续 |
| Python 进程 | 1~2GB | 持续 |
| **日常合计** | **25~35GB** | 96G 绰绰有余 |

**优化原则**：
- `bge-m3` + `qwen3:8b` 常驻
- `qwen3:14b` 按需加载，用完不释放（level1/2 反正也是它）
- `qwen3:32b` 每天一次用完立即释放
- HDBSCAN 聚类是 CPU 密集型，与 LLM 推理错开调度

### 17.3 CPU 推理速度参考

纯 CPU，`qwen3:14b` Q4：
- 单次简报（500 token 输出）：2~5 分钟
- Top-20 全简报：40~100 分钟（可考虑并行度 2~3）
- 建议：简报生成异步，不阻塞主流程

## 18. 反模式清单

| 反模式 | 错在哪 | 正确做法 |
|--------|-------|---------|
| 把全部原始消息给 LLM 总结 | Token 爆炸 + LLM 平均化 + 看不到小而急的新热点 | 先统计发现，再 LLM 解释 |
| 只看绝对提及量 | BTC/ETH 永远第一，看不到新叙事 | 看增长率 |
| 用 LLM 做去重 | 浪费算力，100ms 的活别花 10 分钟 | SimHash/Embedding |
| 单源判断热点 | 被平台噪声/水军误导 | 跨源共振 |
| 固定时间窗口才触发 | 错过爆发前 15 分钟 | 实时激增检测 |
| 把 LLM 当计数器 | 代码更快更准 | 统计交代码，解释交 LLM |
| 把所有消息送给 LLM 聚类 | 该用 Embedding+HDBSCAN | 向量聚类，LLM 只看代表消息 |
| 忽略共现 | 看不到叙事形成 | 共现网络 |
| Phase 1 就上 Embedding | 过度设计，SimHash 够用 | Phase 3 再升级 |
| Phase 1 就上 LLM 简报 | 延迟交付 | Phase 1 只做排行榜 |
| 一次性铺所有层 | 调不通、永远在重构 | 严格 Phase 切分 |
| 用 Markdown 做主要产出 | 查询/消费困难 | 结构化入库，Markdown 只做报告 |
